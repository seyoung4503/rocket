# MPC Hover Bug — Diagnosis & 1-Line Fix

**날짜**: 2026-05-29 16:34 KST  
**버전**: v1  
**Companion data**: [`2026-05-29_1634_v1_hover_bug_fix_results.md`](./2026-05-29_1634_v1_hover_bug_fix_results.md)

## TL;DR

mild divert (78% PID vs 16% MPC) 에서 MPC 가 hover-and-timeout 으로 망한 원인은:

> **`LandingCvxpyWaypointPID` wrapper 의 `lookahead=4` 가 MPC plan 의 *너무 초반* 만 샘플링.**  
> MPC plan 자체는 **멀쩡** (4초 안에 패드 도달). 단지 wrapper 가 0.8초 앞만 보고 PID 에 약한 신호 줘서 PID 가 살살 가다가 timeout.

`lookahead=4 → 10` 한 줄 바꾸니까 mild divert 가 **16% → 90~96%**, 다른 시나리오들도 동시 개선. MPC 가 **처음으로 3/4 시나리오에서 PID 능가.**

## 진단 — 시계열 데이터로 본 진짜 메커니즘

`scripts/diagnose_hover_bug.py` 로 mild divert seed=0 의 한 에피소드 전체를 찍음. 핵심 시점 t=2.66s (패드 점프 0.66초 후):

| controller | xy_off (현재 패드로부터) | PID 가 받은 xy 목표 | MPC plan 의 *끝* (4초 후) |
|---|---|---|---|
| **actuator (lookahead=4)** | 9.94m | **9.12m** (= MPC plan 의 0.8s 시점) | **0.93m** (≈ 패드) |
| **pid (직접)** | 10.32m | (패드 = 0) | n/a |

**결정적 발견**: `pend` 가 0.93m. 즉 **MPC plan 의 *종착점* 은 이미 패드 거의 위**. plan 자체는 정확. 문제는 wrapper 가 plan 의 *초반* (0.8s 시점) 을 PID 에 줬다는 것.

### 결과의 차이

- **actuator (lookahead=4)**: xy_off 10m → 0.5m **~13초** 소요, t=20 timeout 직전에 z=0.29m 까지 내려옴. 실패.
- **pid (직접)**: xy_off 10m → 0.5m **~2초** 소요, t=15.75 에 z=0 도달. 성공 (78% 평균).

PID 단독은 xy_target = 패드 (0,0) 으로 *강한* 횡 명령 → 26°까지 tilt → 빠른 횡 수렴.  
wrapper-MPC 는 xy_target = MPC plan 의 0.8s 시점 (9.12m, 거의 안 움직임) → *약한* 횡 명령 → 느린 수렴.

## 왜 MPC plan 의 0.8s 시점이 약한가

MPC 의 비용 함수:
- `q_pos[xy] = 1.2` (intermediate 추적)
- `q_final_pos[xy] = 45` (terminal 무거움)
- `q_vel = 4.0` (intermediate 속도)
- `r_u, r_du` (smoothness)

→ 옵티마이저는 "4초 동안 *부드럽게* 패드로 가자" plan 짬. 0.8초 시점은 아직 출발 직후라 *거의 안 움직임*. 4초 후엔 패드.

이건 *plan 의 결함* 이 아니라 **수렴이 점진적이라는 정상 거동**. 문제는 wrapper 가 *너무 이른* 시점을 골랐다는 것.

## Fix — 한 줄

`src/rocketsim/controllers/mpc.py`:

```python
class LandingCvxpyWaypointPID:
    def __init__(self, ..., lookahead: int = 10, ...):  # was 4
```

`LandingActuatorAwareWaypointPID` 와 `LandingActuatorAwareMagLagWaypointPID` 의 default 도 같이 10 으로.

### 왜 10 인가 (4와 19 사이)

n=50 sweep:

| lookahead | divert | divert_hard | hard | noisy |
|---|---|---|---|---|
| 4 (현재) | 16% | 56% | 46% | 74% |
| **10** | **90%** | 52% | **68%** | 78% |
| 19 (≈ pad) | 88% | **32%** ⚠️ | 58% | 82% |

`lookahead=19` 는 PID 단독처럼 *즉시 패드 노림* → divert_hard 에서 PID 의 windup 실패 모드 (`too_high`) 재현 (22/50).  
`lookahead=10` 은 sweet spot — divert 풀고, divert_hard 안 망가뜨림.

## 새 시나리오 표 (lookahead=10 적용, n=50, estimated)

| | PID | waypoint | actuator (S1) | actuator2 (S2) |
|---|---|---|---|---|
| hard | 58% | 54% | **68%** | 64% |
| noisy | **84%** | 72% | 78% | 72% |
| divert | 78% | 94% | 90% | **96%** ✨ |
| divert_hard | 18% ⚠️ | **64%** | 52% | 52% |

### 의미 — MPC 가 비로소 PID 능가

| 시나리오 | PID | best MPC | Δ |
|---|---|---|---|
| divert | 78% | actuator2 96% | **+18pp** |
| divert_hard | 18% | waypoint 64% | **+46pp** |
| hard | 58% | actuator 68% | +10pp |
| noisy | 84% | actuator 78% | -6pp (PID 여전히 우위) |

**처음으로 MPC 가 PID 를 *체계적으로* 이김.** noisy 는 외란이 약해서 reactive PID 가 유리한 환경 (앞선 분석과 일관). 그 외 3 시나리오에서 MPC 의 robust 우위 명확.

## Step 1 vs Step 2 — 여전히 동률

| | actuator (S1) | actuator2 (S2) |
|---|---|---|
| hard | 68% | 64% |
| noisy | 78% | 72% |
| divert | 90% | 96% |
| divert_hard | 52% | 52% |

평소처럼 ±4pp 노이즈 안. S1/S2 구분 불가 결론 유지.  
*divert 에서 S2 (96%) 가 S1 (90%) 보다 살짝 좋지만* McNemar 의 discordant 가 작아 통계적으로 유의 미정.

## 시사점

1. **MPC vs PID 비교의 *재출발***: 이전 결론 ("MPC 가 PID 못 이긴다") 는 *wrapper 버그* 때문이었음. 적절한 lookahead 로는 MPC 가 robust 우위.
2. **Step 3 의 *진짜* 평가가 가능해짐**: 이전엔 baseline 자체가 약해서 Step 3 가 얼마나 나아지는지 안 보였을 것. 지금은 강해진 baseline 위에서 Step 3 가 추가 5~10pp 끌어올리는지 검증 가능.
3. **divert_hard 의 PID 18% / MPC 52~64% 격차**: 외란 + 갑작스러운 큰 오차 시나리오에서 MPC 의 plan-기반이 *훨씬* 견고하다는 게 확정됨. 실제 hop 의 비상 시나리오 대비 시 MPC 우선 고려.
4. **noisy 의 PID 우위 유지**: 노이즈 강한 추정기 입력에선 PID 의 D term + 단순 구조가 여전히 유리. 이건 정상적 trade-off.
